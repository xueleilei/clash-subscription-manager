# 定时刷新与保留策略

来源默认每 21,600 秒（6 小时）刷新，可设为 300 秒到 31 天。暂停自动刷新仍可手动刷新，已有节点和发布配置不变。`subscription_source.next_refresh_time` 是唯一的下次调度时间；服务停机很久后只补一次，然后从本次调度时间计算下一次。

手动或定时触发先在 MySQL 建立任务。同一来源有活跃任务时复用其 ID，返回 202 后可通过任务接口查询。4 个工作线程配合 64 个内存排队位置；超出容量的任务仍处于数据库 QUEUED 状态，后续轮询继续安排，不能因进程重启而丢失。

每次执行默认有 300 秒的总租约，可通过 `clash.scheduling.timeout-seconds`（60–3600）调整。内核单次检查和上游请求另有更短的独立超时。超过总租约的任务不得提交，即使超时检查器尚未轮询。定时器发现过期 RUNNING 后记录 TASK_TIMEOUT、为同一来源建立恢复任务，并中断本进程里的旧执行；新的任务有不同 ID，旧执行即使晚到也无法提交。重启后的中断任务最迟在旧租约到期后恢复。第一版建议只运行一个应用副本；数据库版本比较和任务状态仍防止重复提交。

每天 UTC 03:00 执行清理：保留最近 30 天尝试；每套方案保留当前发布和最近 100 个历史发布。当前有效、待处理空结果及保留发布使用的来源快照不会删除。超过 30 天、已无引用的来源快照及已过期/已清空决定可以清理。失效节点 30 天后清除连接秘密，仅保留稳定身份以识别同名恢复；历史发布仍持有其独立加密参数快照。清理不会自动恢复旧成员或提供一键回滚失效凭据。

`clash.scheduling.enabled=false` 可关闭自动轮询和每日清理；手动触发仍会执行。正常生产部署保持默认 true。服务进程异常期间任务继续保存在 MySQL，无需 Redis 或消息队列。
